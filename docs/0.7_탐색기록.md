# 테스트 0.7을 위한 탐색 기록 (2026-11-20)

**원칙**: 테스트(기준월 9~11월)는 보지 않고, 검증(기준월 6·7·8월, 144문제, 롤링)까지만으로 판단했다.
탐색 스크립트는 `ds["dev"]`(기준월 3~8월)만 썼고, 테스트 문제는 메모리에 올리지 않았다.

## 1. 중분류로 내려가 더하기 (bottom-up) — 효과 없음

- 방법: 고객층 × 중분류마다 "다음 달 변화 ÷ 이번 달 대분류 금액"을 회귀로 예측해 더함 → 부호로 방향.
  더한 값이 대분류 증감률과 정확히 같도록 만들었다 (가짜·실데이터 모두 오차 1e-16).
  학습 칸이 4배(432 → 1,728)로 늘어남. 구현: `agents/bottomup.py` (후보 이름 `중분류합산`).
- 결과: 검증 F1 0.41~0.51. 로지스틱(0.55)보다 낮음.
- 원인 진단: **같은 달 안에서 어느 칸이 더 오를지의 순위 신호가 달마다 뒤집힌다.**
  "전월대비 증감률 ↔ 다음 달 증감률" 같은 달 안 순위상관이 3~8월에 −0.48, −0.62, +0.10, +0.22, −0.36, −0.02.
  로지스틱의 검증 순위상관도 −0.25 / +0.19 / −0.03으로 거의 0. 칸을 늘려도 신호가 늘지 않고, 학습 기간의 패턴을 더 잘 외울수록 더 틀림.
- 처리: 코드는 남기고 `config.yaml > 후보모델 > 중분류합산 > 사용: 아니오`.

## 2. 달 전체의 방향 — 가장 큰 효과

- 정답이 '월 합계' 기준이라, 다음 달이 길면 대부분의 칸이 늘고 짧거나 같으면 대부분 준다.
- 검증까지의 6개월(기준월 3~8월)에서 **"다음 달이 더 길다" ↔ "그 달 48문제의 과반이 증가"가 6번 모두 일치**했다.
- Macro-F1은 3개월 144문제를 **합쳐서** 계산하므로, 달마다 방향만 맞혀도 점수가 크게 오른다.

| 방법 (검증 6·7·8월, 144문제) | 검증 Macro-F1 |
|---|---|
| 로지스틱 (지금까지의 기준) | 0.554 |
| 로지스틱 + 달력 차이 변수 (일수·영업일수·휴일수·토일수·쿠폰일수 차이) | 0.583 ~ 0.610 |
| LightGBM·랜덤포레스트 + 달력 차이 변수 | 0.49 ~ 0.59 |
| 일평균 변화 회귀 + 일수 보정 | 0.42 ~ 0.46 (7월처럼 일수가 같은 달에서 틀림) |
| **달력방향: 학습 기간에서 '더 긴 달 / 아닌 달'의 증가 비율을 배워 그대로 적용** | **0.678** |
| 달력방향 + 업종별 예외 / 예외 예측 모델 / 확신 높은 모델로 뒤집기 | 0.53 ~ 0.678 (뒤집을수록 낮아짐) |

- 같은 달 안에서 "어느 칸이 달 방향과 반대로 갈지"는 업종·고객층·변수 어느 것으로도 맞히지 못했다.
  그래서 **검증에서는 0.7을 넘는 방법을 찾지 못했다.** 달 방향만으로 낼 수 있는 상한이 약 0.68~0.70이다.
- 테스트 기간의 다음 달 일수 차이는 +1(9→10월), −1(10→11월), +1(11→12월)이라 세 달 모두 규칙이 방향을 정한다
  (7월처럼 일수가 같은 애매한 달이 없음). 10월은 추석 연휴가 길어 업종별로 다르게 움직일 수 있다는 점은 위험 요인이다.

### 주의 (정직하게 적어 둠)
- "달 길이" 아이디어는 에이전트 이전의 팀 EDA(9개월, 테스트 기간 월 합계 포함)에서 r = 0.71로 처음 나왔다.
  이번 판단은 검증까지의 6개월만으로 다시 확인했지만, 아이디어 자체가 테스트 기간을 전혀 안 본 상태에서 나온 것은 아니다.
- 검증 3개월은 '달' 단위로 보면 표본이 3개뿐이다. 달력방향의 검증 점수도 운의 영향이 크다.

## 3. 에이전트에 넣은 것

| 무엇 | 어디 |
|---|---|
| 후보 모델 `달력방향` (기준: 일수 / 영업일수, 학습 기간에서 증가 비율을 배움) | `agents/calendar_model.py`, `config.yaml > 후보모델 > 달력방향` |
| 변수 `달력차이` (처음값 끄기, 에이전트가 시험) | `agents/data_agent.py > _calendar_diff`, `config.yaml > 변수 > 달력차이` |
| 행 → 문제 대응표 (달력방향·중분류합산이 씀) | `agents/problem_lookup.py` |
| 채택 규칙 ③을 월별 정답률로 볼 수 있게 | `config.yaml > 판단규칙 > 월별_비교_지표: 정답률` (예전 방식은 `macro_f1`) |

- 채택 규칙 ③을 바꾼 이유: 월별 Macro-F1은 한 달 안에서 증가·감소를 섞어 맞혀야 점수가 난다.
  달 방향을 맞히는 방법은 3개월 합친 점수(공식 점수)가 크게 올라도 ③에서 늘 기각됐다. ①부트스트랩 90%·②+0.02는 그대로다.
- 실데이터 검증까지만 돌린 결과 (테스트 안 엶): 모델 담당이 모든 레시피에서 `달력방향`을 채택 규칙으로 골랐다
  (로지스틱 0.554 → 달력방향 0.678, 부트스트랩·상승폭·정답률 상승 월 모두 통과).

## 4. 다음 할 일

1. **최종 실행 1회** (사람이 직접): `.venv\Scripts\python run.py` → 테스트를 한 번 열어 결과 확인.
   결과를 보고 다시 고르면 테스트가 검증이 되므로, 이 실행 결과는 그대로 기록만 한다.
2. 달력방향이 채택된 뒤의 수정 시도는 변수를 바꿔도 달력방향 점수가 같아서 의미가 없다.
   검토 담당이 "선택 모델이 변수를 안 쓰면 변수 수정안을 건너뛰기" 하도록 바꾸면 시도 횟수를 아낄 수 있다.
