# 실패 사례: 검증에서 채택한 수정이 테스트에서는 나빠짐 (검증 과적합)

- 기록일: 2026-11-20
- 대상: 카드 거래 데이터 적용 사례 (고객층 6 × 업종 대분류 8, 다음 달 지출 증가/감소, 테스트 144문제)
- 결과 폴더: `결과/03_agent/runs/<실행>` (저장소에는 올리지 않음)

## 1. 무슨 일이 있었나

에이전트가 수정 루프에서 검증 점수(6·7·8월, 144문제)를 기준으로 **수정을 채택한 모든 실행에서, 테스트 점수가 처음 레시피보다 낮았다.**
수정을 하나도 채택하지 않은 실행이 테스트에서 가장 좋았다.

| 실행 | 모드 | 채택한 수정 | 최종 모델 | 검증 F1 | 테스트 F1 | 처음 레시피 테스트 F1 |
|---|---|---|---|---|---|---|
| 20261120_110937 | 규칙, 수정 3회 | 중분류 분해 | 엑스트라트리 | 0.575 | 0.623 | 0.617 |
| 20261120_111844 | 규칙, 수정 10회 | 중분류 분해 + 소분류 '변동주도' 분리 | 서포트벡터머신 | **0.673** | **0.526** | 0.617 |
| 20261120_114720 | LLM | 소분류 '비소비성' 제외 | 로지스틱 | 0.590 | 0.575 | 0.617 |
| 20261120_121513 | LLM (6개 에이전트) | 소분류 '변동주도' 분리 | 로지스틱 | **0.624** | **0.587** | 0.624 |
| 20261120_114130, 121254 | LLM | 없음 (처음 레시피 A 유지) | 로지스틱 | 0.554 | **0.617** | 0.617 |

비교: 단순 규칙(직전방향유지) 0.360, 사람이 만든 baseline(노트북) 0.520.
모든 실행이 계획서의 성공 기준(테스트 3개월 중 2개월 이상 두 규칙을 이김)은 넘었다.

## 2. 왜 이렇게 됐나 (분석)

1. **검증 문제가 너무 적다.** 144문제의 Macro-F1은 우연만으로 ±0.04~0.08 흔들린다. 채택 규칙(부트스트랩 90% + 상승폭 0.02 + 3개월 중 2개월)을 통과해도 운일 수 있다.
2. **달마다 성격이 다르다.** 같은 모델의 검증 월별 F1이 0.30(6월)~0.63(7월)로 크게 흔들린다. 검증 기간(6~8월)과 테스트 기간(9~11월)은 추석(10월), 소비쿠폰 종료(11월) 같은 행사가 달라서, 검증에서 맞춘 수정이 테스트에서 맞지 않을 수 있다.
3. **시도를 많이 할수록 운으로 이기는 수정이 나온다.** 수정 10회 실행에서 검증 0.673까지 올랐지만 테스트는 0.526으로 가장 낮았다.
4. **'변동주도' 소분류 분리가 두 번 채택됐고 두 번 다 테스트에서 나빠졌다.** 1~5월 통계로 고른 묶음이라, 세금 납부 시기처럼 달마다 다른 패턴이 테스트 기간에는 다르게 나타났을 가능성이 있다.
5. **LLM이 수정을 더 적극적으로 고른다.** 규칙 모드는 정해진 순서로 시험하지만, LLM은 검증 점수가 낮은 달을 보고 "효과가 클 것 같은" 수정(묶음 분리)을 골랐고, 그것이 채택 규칙을 통과했다.

## 3. 에이전트의 안전장치는 제대로 작동했나

- 테스트는 매 실행 한 번만 열렸고, 테스트 점수로 아무것도 고르지 않았다 (`test_log.csv`).
- **"처음 레시피 vs 최종 레시피" 테스트 비교 장치가 과적합을 잡아냈다.** 최종이 처음보다 낮은 실행마다 보고서에 "검증 과적합 의심" 경고가 떴다.
- 즉, 과적합을 **막지는 못했지만 숨기지는 않았다.**

## 4. 함께 발견한 실패: 작은 LLM의 해석 오류

- 실행 담당(gpt-4o-mini)이 테스트 표를 잘못 읽은 일이 두 번 있었다.
  - "규칙1을 3/3개월 이김"을 "2개월"로 씀 (코드가 계산한 숫자를 줬는데도 틀림)
  - 테스트 점수가 검증보다 **높은데** "일반화가 안 됐다"고 거꾸로 해석
- 조치: 핵심 사실을 코드가 문장으로 만들어 주고("확인된_사실"), 실행 담당을 gpt-4.1로 올림 → 이후 해석은 숫자와 일치함.

## 5. 배운 점

- 데이터가 1년치·수백 문제뿐이면 **"많이 시도하고 검증으로 고르기"가 오히려 해롭다.** 처음 레시피(단순한 변수 8종 + 로지스틱)가 가장 안정적이었다.
- 에이전트의 가치는 "점수를 올리는 것"보다 **"올렸다고 착각하지 않게 하는 것"**에서 나왔다 (테스트 봉인, 처음/최종 비교, 결정 기록).
- LLM이 보고서에 쓰는 숫자는 코드가 계산해서 넘겨줘야 한다.

## 6. 다음에 해볼 것

- 채택 규칙을 더 엄격하게 (예: 3개월 모두 상승, 부트스트랩 95%) 하거나 수정 횟수를 1~2회로 줄여서 비교
- 검증 기간을 늘릴 수 있는지 검토 (예: 4~8월 롤링 5회차, 대신 학습 기간이 짧아짐)
